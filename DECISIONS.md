## Decisions so far (as of 2026-10-15)

### Topic and dataset
- Decision: Chose the data-centre / GPU-cluster domain over fintech, market, call-centre and credit-card topics; those were either too common, already covered by earlier work, or not current enough.
- Decision: Ruled out projects that only use linear or logistic regression, since the brief lets us use stronger methods and we wanted room to show real evaluation reasoning.
- Decision: Shortlisted four near-identical "predict a job's runtime/power" datasets: Azure VM, PM100 (Marconi100), Alibaba PAI GPU, and the Parallel Workloads Archive (PWA).
- Decision: Dropped PWA (data is from the 1990s-2000s, fails the "current topic" test) and Azure VM (ranked lower). Final call was PM100 vs Alibaba.
- Decision: Picked Alibaba PAI GPU trace 2020. Reasons: it is AI/ML workloads (the hot, relevant setting), both teammates were more interested in it than power prediction, and it supports two tasks. Trade-off accepted: PM100 had a cleaner licence and a single-file download, which Alibaba lacks.

### Problem framing
- Decision: Two tasks from the same launch request: (A) runtime regression, (B) failure classification. They are parallel branches off one shared pipeline, not stacked; the failure model does not depend on the runtime model.
- Decision: One row = one job. Prediction point: use only what is known at that moment. OPEN (2026-11-04): whether the prediction point is job submission or task launch is to be settled from the README, which describes the job table's start_time as the submission time.
- Decision: Runtime target = log10 of seconds. OPEN (2026-11-04): the exact definition (job end minus job start, which per the README includes queue wait, versus task-level execution time) and which jobs have a usable end time are to be settled by checking the README and data afresh. Failure target = Failed vs Terminated (from the status column); drop Running and Waiting jobs (outcome unknown).
- Decision: Work split: build the shared pipeline together first; Saanvi owns the runtime task, Suchi owns the failure task and the time-shift analysis. Each owns their own evaluation and website interaction (this is what the 5-point individual defense checks). Balanced by giving the runtime side the quantile model and the seen/unseen-user study.

### Data handling
- Decision: Join three tables (job, task, group tag). Keys: per the README, job_name links the job and task tables and inst_id links the group tag table (verify on the data). Collapse the task table to one row per job before joining so we don't inflate row counts; left-join the group tag so it stays optional.
- Decision: Features restricted to launch-time fields: user id, requested CPU/memory/GPU (plan_cpu, plan_mem, plan_gpu), GPU type (gpu_type), instance count (inst_num), task name (task_name), submit hour and weekday (to be re-checked against the README's definition of start_time).
- Decision: Exclude post-outcome fields (end time, final status, anything else known only after the job ends) from inputs; they leak the answer.
- Decision: Categoricals capped at the top 200 values plus an "OTHER" bucket, because HistGradientBoosting allows at most 255 categories per column; revisit once the real cardinality is checked.
- Decision: Leave missing values as missing; the tree method handles them natively.

### Method
- Decision: Main model = gradient-boosted trees (scikit-learn HistGradientBoosting), a regressor for runtime and a classifier for failure. Chosen for mixed numeric/categorical features with missing values and likely interactions.
- Decision: Add a simple regularised reference (ridge for runtime, logistic regression for failure) as an interpretable check and the in-browser model; keep trees only where they clearly beat it.
- Decision: For runtime, also fit a quantile version so the output is a range, not a single number.
- Decision: Baselines to beat: per-user median runtime (global median as floor); per-user failure rate (overall rate as floor).

### Evaluation
- Decision: Split by time, never randomly. Earliest 70% train, latest 30% test, fixed before any comparison (set the cut point before looking at any model results). Reason: in real use the model only has the past, so a random split would leak the future and inflate the score.
- Decision: Walk-forward validation inside the training part for all tuning; the final test set is used once after the model is frozen.
- Decision: Metrics: runtime by MAE and RMSE on log10 seconds (MAE read as a geometric error factor); failure by PR-AUC against the base rate, plus calibration. Report per time band, plus mean signed error per band, quantile interval coverage, paired bootstrap by user for confidence intervals, an ablation ladder, and seen vs unseen users separately.
- Decision: Licence handling: Alibaba has no formal licence; research/study use is allowed and the NSDI '22 paper (Weng et al.) is cited. We will not republish the raw data on the site; only derived results and small summaries, with a link to the source and a fetch script.

### Website
- Decision: Three interactions: (1) "Try a job" live predictor with the baseline shown beside it, running in the browser from exported weights; (2) "Where it wins and loses" error explorer over real test jobs with filters; (3) "Does it hold up over time" error-by-time-band chart. Supporting visuals: calibration plot, ablation bars, error by slice. All precomputed, static on GitHub Pages.

### Observations and gotchas noticed
- Possible label bias for the runtime task (to check). If end times are missing more often for failed jobs, a runtime model trained only on jobs with end times would mostly see jobs that finished normally. Check how end-time availability depends on status before choosing the runtime population, and state the resulting limit. The failure label (status) does not need an end time.
- Possible distribution shift over time (to check). Whether the failure rate or job mix changes across the trace is not measured in this fresh start. The time split and per-band reporting exist so that any shift, if present, is visible.
- Why data can shift over time: users and projects come and go, work arrives in waves, hardware and quotas change, and people change their settings. Common in time-ordered operational data; whether it happens here is to be checked.
- Rows are not independent: jobs from the same user are likely related, so uncertainty is bootstrapped by user (cluster bootstrap), not by shuffling individual jobs.
- Reading the metrics: MAE on log10 runtime, exponentiated, is a multiplicative (geometric) error factor. For PR-AUC, a no-skill model scores at the positive prevalence, so that is the reference line. The ablation ladder is order-dependent: each group's gain is measured given the groups before it.

### 2026-11-04 13:51 UTC — Phase 3: split and validation design (FROZEN before any model was fit)
- [Both] Decision (split, frozen in `results/split.json`, timestamp 2026-11-04T13:51:54Z; no model had been fit at this point): CUT = 70th percentile of submit time over all 1,051,838 jobs = day 55.16. GAP = 24 h embargo. Jobs submitted in [CUT, CUT+24 h) are excluded from every fit and every metric (19,654 jobs). TEST = jobs submitted from day 56.16 to 68.94 (285,306 failure-labelled, 171,672 runtime-labelled). DEVELOPMENT = jobs submitted before CUT whose outcome was known before CUT+24 h (685,529 failure-labelled, 545,646 runtime-labelled). Only 77 development jobs are dropped because their outcome arrived later.
- [Both] Decision (why a gap and a known-by rule): A model deployed at the start of the test period can only have learned from outcomes known by then. Without the rule, a long training job finishing during the test period would leak test-period information into training. The gap also stops near-duplicate repeated jobs straddling the cut from appearing on both sides within minutes. Alternative rejected: no gap (simpler, but leaks at the boundary).
- [Both] Decision (walk-forward folds, all tuning happens here): 3 folds with cuts at days 34, 41, 48. Fold k fits on development jobs submitted before c_k whose outcome is known by c_k+24 h, and validates on jobs submitted in [c_k+24 h, c_{k+1}) with c_4 = CUT. Validation sizes: 77,779 / 84,975 / 106,832 failure-labelled jobs. Model selection uses the mean over the 3 folds. Days 0–5 (warm-up, under 130 jobs/day) stay in every fit set.
- [Both] Decision (reporting bands): The test period is split into 4 bands of equal duration (≈3.2 days each; edges at days 56.16 / 59.35 / 62.55 / 65.75 / 68.94). The day 59–60 burst falls in band 2. Band 1 = 78,289 failure-labelled jobs, band 2 = 103,063, band 3 = 57,941, band 4 = 46,013.
- [Both] Decision (final test protocol): Models, features, hyperparameters, calibration and the alert threshold are frozen from walk-forward results, then refit once on all development rows. `src/final_test.py` runs the test exactly once and writes `results/test_run_log.json` (timestamp, git commit, model list). Re-running it requires `--force` and a DECISIONS.md entry.
- [Saanvi] Decision (runtime metrics): MAE and RMSE on log10 seconds; 10^MAE as the typical multiplicative error factor; median absolute error; mean signed error (prediction − truth) overall and per band; for the quantile model, empirical coverage of the 5–95% interval (target 90%) and mean interval width.
- [Suchi] Decision (failure metrics): PR-AUC against the base rate (the no-skill line); ROC-AUC as secondary; Brier score against the base-rate Brier; expected calibration error with 10 equal-frequency bins; reliability diagram. Alert threshold is cost-justified: a missed failure costs 3 units, a false alert 1 unit (C_FN/C_FP = 3), so the Bayes-optimal threshold for calibrated probabilities is 0.25. The operating threshold is chosen by minimising this cost on the walk-forward folds, never on test. The site's slider shows the trade-off at other thresholds.
- [Both] Decision (comparisons): Every headline number is reported against its baseline, with a 95% CI from a paired bootstrap that resamples users (1,000 replicates; seed 335). Ablation ladder on the final HGB models: global floor → per-user baseline → resources → + task type → + history → + time. Seen vs unseen: (a) user present in development vs not (1.45% of test jobs), and (b) job with no finished history at submission vs with history. Sensitivity runs (never headline): + assigned `gpu_type` (leakage size), heavy user excluded, and random split vs time split.
- [Both] Decision (random-vs-time split demo): To show how a random split inflates scores without touching the test set, this comparison is run inside development only: time-ordered (fold 3) vs a random split of the same development rows with the same validation size.

### 2026-11-04 — Phase 5: models (walk-forward folds only; test set never loaded)
- [Both] Decision (preprocessing inside every fit): Trees: the train-only `CategoryEncoder` (top-200 + OTHER for `user_id`, all train levels for the others, unseen → OTHER) and native NaN handling. Linear models: log1p on heavy-tailed counts, median imputation with missing-value indicators, standardisation, one-hot (max 201 levels, infrequent/unseen → one bucket). All fitted on the fold's fit rows only (`src/model_common.py`). Early stopping is disabled so no random internal holdout mixes time.
- [Saanvi] Observation (runtime, mean fold MAE log10 s): per-user baseline 0.569; ridge 0.352 (alpha 0.1 / 10 / 1000 → 0.352 / 0.352 / 0.360); HGB squared loss 0.316–0.319; HGB absolute loss 0.300–0.306. Best: HGB absolute loss, learning rate 0.1, 127 leaves, min leaf 100, 300 iterations, MAE 0.2995. It beats ridge on every fold.
- [Saanvi] Decision: The runtime model is the HGB regressor with absolute-error loss. It clears the pre-stated keep rule over ridge (better by > 0.02 on the mean and on every fold). Absolute loss is chosen because the headline metric is MAE (whose optimum is the conditional median). Trade-off accepted: its RMSE (0.508) is worse than the squared-loss tree (0.501), and both metrics are reported.
- [Saanvi] Problem → Fix (interval under-coverage): the raw 5–95% quantile interval covered only 77.7% / 80.3% / 78.5% of validation-week runtimes (target 90%). The intervals were too narrow for the next week because the next week is not like the training weeks. Fix: conformalised quantile regression (CQR). Learn an additive widening on one validation week and apply it forward. Fold check: offset from fold 1 applied to fold 2 gives 90.7% coverage; fold 2 → fold 3 gives 88.2%. The final model uses the offset learned on fold 3 (0.183 log10, i.e. both ends widened by ×1.53). Raw and corrected test coverage are both reported.
- [Suchi] Observation (failure, mean fold PR-AUC): base rate 0.194; per-user baseline 0.494; logistic 0.709 (C = 0.01; 0.1 → 0.707; 1 → 0.705). The pre-registered HGB grid scored 0.644–0.676 and got worse as capacity grew; class weighting did not help ranking (0.644–0.672) and hurt Brier.
- [Suchi] Problem → Fix (trees overfit the training period): a tree that fits the training weeks closely learns patterns (bursts, particular users' episodes) that do not carry to the next week. We extended the grid on the folds only, in the direction the folds pointed: smaller, regularised trees (15 or 7 leaves, min leaf 2,000–5,000, L2 = 1). Best: 0.7105 vs logistic 0.7088, a tie that does not clear the keep rule (> 0.02 and every fold; the tree only wins fold 1). Decision: logistic regression is the failure model. The regularised tree is reported as a comparator. Lesson recorded for the viva: more complex is not automatically better under drift.
- [Suchi] Observation (calibration): isotonic recalibration, fit on the previous fold and applied forward, made Brier worse on fold 2 (0.0847 → 0.0859) and better on fold 3 (0.1061 → 0.1035). The pre-stated rule needed improvement on both folds, so it is not used. Logistic regression is already close to calibrated where the failure rate is stable (fold 2 ECE 0.017) and under-predicts when the rate rises (fold 3 ECE 0.052).
- [Suchi] Decision (threshold): the fold-pooled cost (C_FN = 3, C_FP = 1) is minimised at 0.17, below the Bayes value of 0.25. That is consistent with the model under-predicting risk when the failure rate climbs between weeks. The operating threshold is 0.17, chosen on folds 2–3, never on test.
- [Both] Decision: The ablation ladder and the assigned-GPU sensitivity run use each task's chosen family (runtime: HGB; failure: logistic), so they describe the models we actually report.
- [Both] Decision: Before the single test run, the full pipeline was dry-run with fold 3 standing in for test (tiny models, development rows only) to catch code errors. `results/test_run_log.json` did not exist before the real run.

## Resume summary
- Built an end-to-end ML pipeline on Alibaba's production GPU-cluster trace (1.06 M jobs, 1,433 users, 69 days) that predicts, at submission time, a job's runtime and its risk of failure, with a leakage-audited feature set and time-safe user/script history features verified by brute force.
- Runtime: a gradient-boosted model cut the typical error factor from ×4.0 (user's past median) to ×2.2 on a held-out later period. MAE 0.338 vs 0.601 log10 s, paired user-bootstrap 95% CI for the difference [−0.32, −0.18]. Conformal quantile intervals reached 88.6% coverage against a 90% target (raw: 75.6%).
- Failure: logistic regression beat the per-user failure rate on the full test set (PR-AUC 0.923 vs 0.542, base rate 0.398; CI of difference [+0.09, +0.42]). In a pre-planned sensitivity analysis without the dominant user: 0.614 vs 0.475 at a base rate of 0.151. Gradient-boosted trees overfit the training weeks and were rejected by a pre-stated keep rule.
- Designed and enforced the evaluation protocol: time split frozen before modelling with a 24 h embargo, walk-forward tuning, test scored once and logged, cluster bootstrap by user. Showed that a random split would have overstated runtime accuracy (MAE 0.20 vs 0.33).
- Hardest problems solved: label bias (failed jobs almost never record an end, so runtime was scoped to successes), leakage from the scheduler-assigned GPU type (excluded; quantified as a sensitivity run), interval under-coverage under drift (fixed with forward conformal calibration), and a test period dominated by one user (reported transparently as a sensitivity analysis). Shipped as a static, accessible interactive site with seven evidence-driven panels.
